## Summary

The ledger holds up. The SpecTec rules confirm every one of the five
`deviates` entries, and the simulator confirms four of them. The simulator
also reproduces the copy-back finding. Every sampled `same` entry cites a
rule that really decides the behavior it names.

I found the following problems:

- **Shifts.** The `same` entry is wrong above 2048. For a shift amount over
  2048, SpecTec's builtin `$shl`/`$shr` stops with the error "shift amount
  too large" (confirmed on the simulator). p4blo returns `0`.
- **Copy-back target.** The entry misses one case: the result lvalue of an
  extern call is also resolved after copy-out.
- **`hs.lastIndex` in controls.** The validator accepts it, but P4 and
  SpecTec's typing allow it only in parsers. The printed program fails
  SpecTec's typing.
- **`hs.last` elaboration.** The elaboration used in coverage.md is not
  faithful at `nextIndex == 0`. SpecTec rejects with `StackOutOfBounds`
  there; p4blo returns a zero invalid header.
- **Two `refines undefined` entries** ("Key expressions" and "Priority
  outside ternary tables") mix in domain restrictions on behavior SpecTec
  does define.

The ledger test rejects every kind of single corruption I tried. It cannot
see two entries swapping classes, and it accepts some names that resolve
only through imports.

## Confirmed defects

### D1. Copy-back re-resolves the argument lvalue (both interpreters)

The ledger's own finding is real.

**Where.** Both interpreters write through the syntactic lvalue after the
callee returns:

- `spec/ir/P4bloIR/Exec.lean:179-184` (`copyBack` calls `writeLValue lv v`).
- `impl/python/p4blo/interp/stmt.py:144-149` (`copy_back` calls
  `write_lvalue(arg.lvalue, ...)`).

`writeLValue` evaluates the `.index` expression again at write time
(`Eval.lean:245-250`). SpecTec does not:

- `Copy_in_arg/inout` and `Copy_in_arg/out` (8.10.2) call
  `Argument_eval_lvalue` → `Lvalue_eval/base-cont-index-cont`. That
  evaluates the index into a storage reference `ref[integerValue]` once.
- `Copy_out_argument/non-dontcare` (8.10.3) writes through that stored
  reference.

**Reproducer.** The program is `$S/cb/cb.txtpb`. Control `C` has a local
`t: bit<8>` and an action `a(inout h8 x) { t = 1; x.f = 170; }`. The body is
`t = 0; a(hdr.hs[t]);`. The parser extracts `hs.next` twice, and the
deparser emits `hs`.

The validator returns no errors (`validator.validate(p) == []`).

```
nix develop -c uv run python $S/cb/run_py.py $S/cb/cb.txtpb 0000 $S/cb/cb.p4
  -> python out: [(0, '00aa')]
nix develop -c uv run python $S/cb/run_lean.py $S/cb/cb.txtpb 0000
  -> lean out: port 0: 00aa
nix develop -c uv run python tests/oracle/run.py -v $S/cb/cb.txtpb $S/cb/cb.stf   # expect AA 00
  -> PASS  [PASS] Transmitted (0) AA00
```

Both interpreters write `hs[1]`; SpecTec writes `hs[0]`. The printed P4
(`$S/cb/cb.p4`) is `a(hdr.hs[t]);`, with the action writing `t`.

**The alias check.** The validator's alias check was right to accept the
program. `check_args` (`validator.py:991-1047`) forbids overlapping
*storage* between two out/inout arguments. Here there is one argument, and
its index reads a variable that the callee writes as a block variable. That
is a dependency, not an alias, so no rule of this form catches the action
case. A validator-only fix would have to reject:

- any out/inout argument with a computed index when the callee can write a
  variable the index reads. For an action, that is every block variable
  the action body writes, directly or through the actions it calls. For a
  block or extern call, it is every other out/inout argument.

That is possible, but it is a restriction, not a fix.

**A case the entry misses.** An extern call's result lvalue is resolved
after the out arguments are written:

- `Exec.lean:219-222` and `stmt.py:227-230` handle the result after the
  loop that writes the out arguments.
- In SpecTec, `x = e.m(...)` is `Stmt_eval/typedLvalueIR-cont-eq-typedExpressionIR-cont`.
  It runs `Lvalue_eval` on `x` *before* it evaluates the call.

So `hs[t] = r.m(t)`, where `t` is an out argument, differs in the same way.
I derived this from the code and the rules and did not run it: no extern
family has both an out parameter and a return value.

**What a correct fix touches.**

1. **Resolution helper.** Add `resolveLValue : LValue → M LValue` in
   `Eval.lean` and `resolve_lvalue` in `expr.py`. They replace each `.index
   base e` by `.index base (literal i)`, with `i` evaluated now. They must
   be the identity on index-free lvalues, and must leave `.next` alone
   (SpecTec keeps `.next` symbolic).
2. **Resolve at copy-in.** Apply the helper in these places:
   - Lean: `.action` and `.block` in `Execution.dispatch`, and in
     `callExtern`, including the `result` lvalue before the call.
   - Python: `call_action`, `call_block` and `call_extern`.
3. **Carry the resolved lvalues.** Carry them to copy-back through
   `Work.actionReturn` and `Work.blockReturn` (or change `copyBack`'s
   argument), and do the same in Python.

**Lean proofs that mention copy-back or its work items.** In `spec/ir/`:

- `P4bloIR/PlainCallReturn.lean`: `copyBack_three`, `dispatch_return`,
  `return_step`, `return_steps`, `returned_*`.
- `P4bloIR/PlainCallEntry.lean`: `argument_in/inout/out`, `dispatch_entry`,
  `entry_steps`.
- `ProofAudit.lean`, which prints the axioms of `copyBack_three`.
- `Tests/PlainCallReturn.lean`, `Tests/PlainCallEntry.lean`.

In `impl/lean/P4blo/`:

- `CallEntry.lean`: `source_entry*`.
- `GuardedControlCall.lean`: `call_correct`, `source_steps`, …
- `ForwarderAction.lean` and `ForwarderApply.lean`, whose `.actionReturn …
  none` items change shape if the payload does.
- `GuardedCallPrefix.lean`, `TutorialFirewall*.lean`.

The plain-call profile uses only `.var` arguments. If resolution is the
identity there, one rewriting lemma should carry those proofs.

**Also needed.** Add a conformance test (`test_lean_agrees…`). The entry's
`Test:` line cites two tests that never exercise the difference.

### D2. `hs.lastIndex` is accepted in controls but is P4 only in parsers

- `validator.py:1129-1133` types `last_index` anywhere.
- SpecTec's `Expr_ok/headerStack-lastIndex` (5.06.1:819-834) requires
  `TC.BLOCK.KIND = PARSER` or a parser state, as P4 §8.18 does.
- `tests/test_interp_control.py::test_last_index_wraps_at_next_index_zero`
  exercises it in a control.

**Reproducer.** `$S/cb/li.txtpb` is `cb.txtpb` with
`t = (bit<8>) hdr.hs.lastIndex` in control `C`. The validator returns
`[]`, and it prints `t = (bit<8>) hdr.hs.lastIndex;`. `p4spectec sim … -p
$S/cb/li.p4` fails with `relation V1Model_init failed … condition
(expression'' = ((THIS) as expression)) was not met`.

This breaks "every validated program prints to P4". The corpus uses
`last_index` only in parser blocks (checked in acl, stacks and
subparser_stack), so no oracle run shows it.

**Fix.** Reject `last_index` outside parsers in the validator, and in the
Lean validity check if there is one. Then the "`hs.lastIndex`" entry should
state the parser-only rule.

### D3. The `hs.last` elaboration is not the language's at `nextIndex == 0`

- `docs/coverage.md:115` elaborates `hs.last` as `Index(hs, LastIndex(hs))`.
- The stacks README calls that "how the language defines it".
- SpecTec's `Expr_eval/stack-last-out-of-bounds` and
  `Lvalue_eval/stack-last-out-of-bounds` reject with `StackOutOfBounds`
  when `nextIndex < 1` or `nextIndex > size`.
- p4blo evaluates `hs[2^32-1]`, which gives a zero invalid header and no
  error.

**Reproducer.** In `$S/sim/plast.p4`, a v1model parser runs `hdr.o.a =
hdr.z.last.f;` with `z` empty. Ingress writes `o.h = 1` if `parser_error ==
StackOutOfBounds`. `p4spectec sim` transmits `…0100`, so `o.h = 1`:
StackOutOfBounds.

The printed form, `hs[hs.lastIndex]`, is self-consistent on SpecTec, where
it gives `hs[0]`. But the elaboration changes the meaning of the source,
which matters for claim 1 and the A5 bridge.

**Suggested fix.** Add a ledger entry (class `deviates`, or record it as an
elaboration that needs a `verify`/guard) and correct coverage.md.

### D4. Shifts by more than 2048 have no SpecTec outcome

The rule `$bin_shl` is unbounded. But the builtins `shl`/`shr`
(`p4spec/lib/interface/builtin/numerics.ml:45-69`) raise "shift amount too
large" for offsets above `max_bit_width = 2048`.

**Reproducer.** In `$S/sim/probe.sh sh2`, control `bit<16> k = 16w2049;
hdr.o.b = hdr.o.a << k;` gives `relation V1Model_ingress failed … shift
amount too large`. `>>` by 3000 does the same (`sh3`). With `k = 2048`, it
passes and gives `0`.

p4blo gives `0` for any amount. The "Shifts" entry says *same … whatever
the amount's width*. Suggested fix: add to the entry that SpecTec's
simulator has no outcome for amounts over 2048, and list it among known
oracle limitations.

## Unsure entries resolved

- **Recursion.** Keep `not representable`. SpecTec's typing rejects a
  self-recursive action: `$S/sim/rec.p4` (`action a() { a(); }`) fails at
  `callResolution … matches pattern (_) was not met`. P4's
  declaration-before-use rule rules out mutual recursion between actions,
  and instantiation rules it out between blocks. Nested non-recursive
  action calls run (`nested.p4`, `o.a = 09`). The Lean line cites
  `Execution.drive`, which does not implement the rule; the check is
  validator-only (`check_call_graph`), and the entry should say so.
- **LPM.** Confirmed `refines undefined`.
- **Priority outside ternary tables.** Doubtful: an input restriction, and
  `same` on the accepted domain (see the table above).
- **Canonical entries.** Right for host entries. For `const entries` it
  rejects behavior SpecTec defines (see the table above).
- **Entries name their action.** Acceptable, with the sentence fix above.
- **Table miss.** `same`: `$select_action(TBL, eps)` returns
  `TBL.DEFAULT_ACTION`.
- **Comparison.** `same`, with the header deviation inherited, as the entry
  already says.
- **Deparser sub-blocks.** `same`: SpecTec runs the sub-deparser through
  `Call_eval/controlApplyMethodCallee`.
- **Errors.** Acceptable, with the softened sentence above.

## Missing behaviors

These are closed by the code but have no ledger entry:

1. **`hs.last` at `nextIndex == 0`** (D3). This is `deviates`, or an
   elaboration defect.
2. **`hs.lastIndex` outside parsers** (D2). It should be excluded, not
   closed.
3. **Extern result lvalue resolved after copy-out** (D1). Fold it into
   "Copy-back target".
4. **Actions read and write their block's variables.** `withAction` and
   `.actionReturn` restore the frame with those writes before `copyBack`.
   SpecTec: `$inherit_e(p_shared, …)`, then `Copy_out`'s
   `$copy_e(p_shared, …)` before the per-argument writes. It is `same`,
   with the same order (block writes first, then copy-back). The copy-back
   entry relies on it but no entry states it.
5. **Boolean header fields take one bit.** In Lean, `fieldFromBits` reads
   `chunk == 1` and `fieldBits` writes one bit. SpecTec does the same:
   `$write_value_from_bits'(_B _, …)` takes one bit, and
   `$write_bits_from_value(_B b) = [b]`. It is `same` but unlisted; the
   "Extract sets the target valid" and "emit" entries speak only of bits.
6. **State-local variables (elaboration note, lower confidence).**
   `ParserState_eval` wraps each state in `$enter_e` and `$exit_e`, so a
   variable declared without an initializer inside a state gets `$default`
   again on every entry. p4blo has only block locals (coverage.md:175 and
   186). A hoisted state-local with no initializer keeps its value across
   revisits unless the frontend inserts a zeroing assignment. Say in
   coverage.md which it does.
7. **Oracle limits worth listing where the entries cite the rule:** shifts
   over 2048 (D4), and the 9-arch mask-from-base defect (already in
   `tests/oracle/README.md`).

I found nothing else in `Eval.lean`, `Exec.lean`, `Tables.lean` or
`Packet.lean` that goes unlisted.

Other weaknesses, none serious:

- `resolve_python` accepts a name that exists in a module only by import.
  For example, `p4blo.interp.stmt.evaluate` resolves because `stmt.py`
  imports `evaluate`. Requiring `obj.__module__` to match the prefix would
  make it strict.
- `reference_problem` accepts any top-level function or class, so a helper
  such as `tests/test_interp_control.py::run` passes as a test id.
  Requiring a `test_` prefix, or collecting with pytest, would fix that.

  but a `Lean:` line could cite a lemma rather than the implementing
  definition.
