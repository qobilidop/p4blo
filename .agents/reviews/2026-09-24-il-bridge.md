# Review: the IL bridge (A5), `work/il-bridge`

Branch tip reviewed: `c78f055` (eight commits on `5e4aa8e`), read from a
`git archive` of that commit, since the worktree was removed during the
review. Date: 2026-09-24. The oracle was the variant checkout
`~/.cache/p4blo/p4-spectec-il-bridge`, not rebuilt. BMv2 was the existing
`p4blo-bmv2` image, not rebuilt. Probe programs are under the session
scratchpad's `probes/` directory. Each has a `.p4` file, a `.stf` file and
`cmp.sh <name>`, which runs SpecTec `sim` and the bridge plus Python
interpreter on the same vector.

## Summary

The bridge does what it claims on the programs it was measured on.

- `tests/test_frontend_spectec.py` passes: 82 tests in 37 s under
  `P4BLO_REQUIRE_IL_EXPORT=1`.
- The census reproduces exactly: 191 programs, 103 translate, 98 pass.
- The five new p4c programs give byte-identical outputs on SpecTec, on
  every packet. Two of them are also byte-identical on BMv2.
- The patch is deterministic and applies cleanly, with or without `0001`.
- Ruff and pyright are clean.

Four confirmed defects, all found with small P4 programs outside the
corpus:

1. **Hoisted locals are not re-defaulted per entry.** This affects locals
   declared in a parser state or an action, and the locals and `out`
   parameters of inlined functions. It covers header validity, which P4
   defines.
2. **A block's extern state is shared across instantiations.** This
   happens when the block owns the state only through a sub-block.
3. **A user `M` field is not always renamed away from the contract.** When
   the source also uses the matching `standard_metadata` field, the user
   field becomes the contract field.
4. **Compound shifts are never translated.** Neither `<<=` nor `>>=` by an
   unsized constant translates, although the compound-assignment row is
   marked "performed".

Two more behaviours of the reverse shim change meaning silently instead of
refusing:

- writing `egress_spec` after `mark_to_drop`;
- writing `egress_spec = 511` directly, which lets egress side effects run.

Of the fourteen rows that moved to *elaborated*, eight are exercised by no
test.

## Confirmed defects

### D1. State-, action- and function-local variables keep their value across entries

`blocks.py:1131` (`_var_decl`) hoists every declaration to `Block.locals`.
When there is no initializer it emits nothing. `translate_action`
(`blocks.py:1590`) and `_inline` (`blocks.py:1496`) reuse the same path.

**Parser state.** Probe `probes/statelocal.p4`: a looping state declares
`bit<8> cnt; h_t tmp;`, increments `cnt` and counts `tmp.isValid()`. It
runs on three stack elements.

| Run | Output | `cnt` | `tmp` valid on re-entry |
|---|---|---|---|
| SpecTec | `010000` | re-defaulted each entry | never |
| Bridge | `030200` | accumulates | seen twice |

**Action.** Probe `probes/actlocal.p4`: an action declares `h_t tmp;`,
bumps a field if `tmp.isValid()`, then calls `tmp.setValid()`. It is
called twice. SpecTec outputs `0000`; the bridge outputs `0001`.

The scalar case is P4's "unspecified" read, where SpecTec defaults to
zero. The header case is not: P4 defines an uninitialized header local as
invalid. So this is a change of defined behaviour.

The same applies to `_inline`:

- its `out` parameters and body locals are per-call-site block locals;
- they are never reset;
- so an inlined function in an action or state that runs twice sees stale
  values.

This settles the ledger's open "State-local variables" question as far as
the bridge goes: **the bridge does not re-default.** The coverage page
says so only for parser states (rows 190 and 201), and only as undecided.
Action and function locals are not mentioned.

**Suggested fix:** at every declaration without an initializer, except
block-level locals, write the default where the declaration stood. That
means zero for scalars, `setInvalid` for headers, and recursion into
structs and stacks. The same fix covers `out` parameters of inlined
functions.

### D2. Extern state shared through a stateless intermediate block

`owns_state` (`blocks.py:2312`) looks only at a block's own extern
instantiations. `sub_block` (`spectec_il.py:420`) uses it to decide
whether each instantiation gets its own block.

Probe `probes/shared.p4`: control `B` owns `register<bit<8>>(1)` and
increments it. Control `A` instantiates `B()`. Ingress instantiates
`A() a1; A() a2;` and applies both.

- P4 (SpecTec): two registers, output `0101`.
- Bridge: `a1` and `a2` map to one block `A`, and so to one `B` and one
  register. Output `0102`.

`owns_state` must be transitive: a block owns state if it, or any
sub-block it instantiates, does. With direct application
(`B.apply()` inside `A`), the fix also needs that call site to count.

### D3. The contract-field collision is renamed only when `standard_metadata` does not use that field

`_rename_user_contract_fields` (`v1model.py:569-588`, skip at line 579)
treats a user `M` field named `egress_port`, `drop`, `ingress_port` or
`parser_error` as the contract field whenever the source reaches the
corresponding `standard_metadata` field anywhere.

That is right for the printer's own output, which keeps the two in sync.
It is wrong for arbitrary P4.

Probe `probes/collide.p4`: `struct M { bit<9> egress_port; }`, then
`sm.egress_spec = 3; meta.egress_port = 5;`.

- SpecTec: the packet leaves on port 3.
- Bridge: the packet leaves on port 5.

Coverage row 274 says "a user field named like a contract field is
renamed", which overclaims. The same root cause turns a user
`bool drop;` scratch flag into the drop decision whenever `mark_to_drop`
appears anywhere.

**Suggested fix:** rename every user field that collides, and have the
shim write the contract fields itself. Failing that, refuse
(`NotTranslated`) when a colliding user field is written other than in
the printer's exact synchronizing pattern.

### D4. `x <<= c` and `x >>= c` with an unsized constant are refused

`_assignment` evaluates `rhs = self.expr(value)` first (`blocks.py:1161`,
and the same at `blocks.py:1234` for slices). `expr` raises
`NotTranslated("intTypeIR (INT)", "the unsized 2 has no width here")` on
the bare `int`. So the `Int` special case in `_compound`
(`blocks.py:1184-1188`) can never be reached.

Probe `probes/shift3.p4` (`hdr.h.f <<= 2;`) fails to translate. The plain
form `x = x << 20` translates, and it agrees with SpecTec
(`probes/shift2.p4`).

Row 167 says "performed; `/=` and `%=` on values not known at compile time
are not attempted". It should also name the shifts, or the code should fold
the shift amount before calling `expr`. There is also a latent bug if that
branch is reached: it builds `lit_bits(width_of(lt), v)` without the
over-width guard that `_binary` has (`blocks.py:683`). An amount of
width or more (`bit<4> x; x <<= 20`) would produce an out-of-range
literal.

## Golden differences

- **acl.** Both differences are non-semantic:
  - key `Key.name` values (p4c STF names versus P4 control-plane paths);
  - `setbyte`'s marker write of 4, which no label reads (the marker
    starts at 0, and no label is 0 or 4).

  Replayed independently: `ternary2.stf` gives 4/4 packets identical. The
  program has no extern instances, so there is no state to compare.
- **forwarder.** Non-semantic:
  - the unread contract field `ingress_port`;
  - `egress_port = 511` inside `drop()`. It is followed only by
    `update_checksum`, and the packet is dropped.

  All five vectors are identical, including the one drop (`miss.stf`). The
  only instance is the stateless `checksum16`.
- **stateful.** Genuinely the golden's own additions:
  - the counter;
  - the seed guard;
  - the name `pipeline`.

  `persist.stf` is expected to differ and does.
- **priority.** A real behavioural difference: the golden's `IR = 4 - p4c`
  against the IL's first-listed-wins order.

  The docstring of `_documented_priority` and `docs/assurance.md:387`
  describe it as "P4-SpecTec's" reading kept against p4c and BMv2. Main's
  2026-09-24 "Entry priority" decision now makes the specification's order
  the reference and re-derives the golden. Once the golden changes, the
  "documented" status fails by design (the test asserts a difference),
  and these texts need rewording.

## Reverse shim

Each case below was run through SpecTec, and on BMv2 where useful. Probes
are in `probes/`.

| Case | v1model / SpecTec | IR via bridge | Verdict |
|---|---|---|---|
| `mark_to_drop(sm); sm.egress_spec = 2;` (`undrop`) | forwarded to port 2 | dropped (`drop` stays true) | **Meaning change.** The docstring and assurance.md mention it; coverage rows 262 and 274 do not. |
| `mark_to_drop(sm); f = sm.egress_spec >> 1; sm.egress_spec = 1;` (`readspec`) | port 1, `f = ff` | dropped | The read is faithful. The later write is lost, as in `undrop`. |
| `sm.egress_spec = 511;` with an egress register (`port511b`) | dropped; egress does not run; the next packet reads 1 | dropped, but egress runs (`drop` is not in the contract, so it is not gated); the next packet reads 2 | **Meaning change** in extern state. |
| `mark_to_drop` then a register in egress (`dropgate`) | egress skipped | egress gated off | Correct. |
| `verify_checksum` with a bad checksum, `checksum_error` unread (`vcsum`) | forwarded | forwarded | Correct. A read of `checksum_error` is refused (`checksum2-bmv2`, `checksum3-bmv2`). |
| `hash` with crc16, csum16 and crc32; base; power-of-two `max`; narrower result (`hashp`) | BMv2: `12340010edcb189996a307` | identical to BMv2 | Correct. SpecTec's crc16 differs from both; that is the known SpecTec CRC discrepancy (`tests/test_crc.py`), not the bridge. |
| user `M.egress_port` next to `sm.egress_spec` (`collide`) | port 3 | port 5 | **D3.** |

Also checked and correct:

- **Merging controls.** The merge maps parameters by position with
  `standard_metadata` dropped, so the verify and compute controls line up.
  Locals are renamed on collision. An action or table clash is refused.
- **`_drop_printed_epilogue`.** It only removes a no-op at the end of the
  control.

**Suggested fix for both silent drop cases:** translate v1model's rule
literally. That means:

- `mark_to_drop` → `egress_port = 511`;
- `egress_spec = e` → `egress_port = e`;
- at the end of the ingress part, `drop = (egress_port == 511)`;
- then gate egress on `!drop`.

This is exact for everything the source can write. Otherwise, refuse a
write to `egress_spec` that may follow `mark_to_drop`, and a constant 511.

## Replay conventions

All five new programs were compared on SpecTec `sim` using exact
transmitted bytes, not the STF's masked expectations:

| Program | Packets | Result |
|---|---|---|
| `gauntlet_side_effects_in_mux-bmv2` | 2 | identical |
| `issue-2123-3-bmv2` | 22 | identical |
| `issue1000-bmv2` | 16 | identical |
| `issue3488-1-bmv2` | 3 | identical |
| `issue995-bmv2` | 11 | identical |

SpecTec passes every vector itself. On BMv2 (the `p4blo-bmv2` image, the
source compiled directly), `gauntlet_side_effects_in_mux-bmv2` and
`issue3488-1-bmv2` are also byte-identical to p4blo. That includes the
bytes the STF masks with `**`.

So the conventions hide no divergence on these programs:

- per-port queues;
- unique suffix key matching (an ambiguous match is left unresolved);
- `$0` read as `[0]`;
- 64 ports, so that 511 drops.

Two caveats:

- Per-port matching cannot tell which input packet produced an output.
- None of the five vectors installs table entries, so the suffix
  key-matching path is exercised only by the census.

## Patch

`0002-il-export.patch`:

- **No change to existing behaviour.** It adds a library
  (`backend-il/`), a re-export in `p4spec/lib/dune`, and one command
  registered in `main.ml`. `Inst.Hook.register []` runs only inside the
  new command.
- **Applies cleanly.** Checked on a pristine archive of `2730cfd9`: alone,
  after the branch's `0001`, and after main's current `0001` (main has
  changed `0001` since).
- **`build.sh` applies it.** The script globs `patches/*.patch` in name
  order and digests every patch into the stamp, so the builder did not
  need to edit it.
- **The variant oracle's stamp matches.** It reads
  `2730cfd9… befbb6a547f1e341e487c2be40de7b36b0eb21b7`, which is exactly
  the digest of the branch's `0001` plus `0002`.
- **The JSON is deterministic.** Three exports of `issue3488-1` and two of
  `firewall.p4` hash identically. The output contains no filesystem paths.
- **CI.** `.github/workflows/oracle.yml` runs the module with
  `P4BLO_REQUIRE_IL_EXPORT=1`, and the cache key covers `patches/**`.

  Worth one sentence.

  p4blo's block architecture and the `block` command". It should mention
  `il-export`.
- `tests/test_frontend_spectec.py:167-175` and `docs/assurance.md:387-390`:
  reword the priority text under main's "Entry priority" decision.
- **Readability.**
  - `blocks.py` is 2328 lines, and `BlockCx` holds expressions, lvalues,

    expressions and lvalues from statements and tables would follow the
    module's own sections.
  - `_expr_lvalue` (`blocks.py:942`) is a pure alias of `lvalue_of_expr`.
  - `_wrap` is underscore-private in `common.py` but imported by three

  - `translate_block`'s `meta_index` values are magic numbers
    (`spectec_il.py:408`).

    `V1Model.extern_object` takes `BlockCx | None`.
  - The `_pad` comment (`blocks.py:1271`) is hard to follow.

## Anything else

- **`normalize` renaming.** It renames locals to `v0`, `v1`, … without
  checking against action parameter names. An action parameter called
  `v0` would capture a renamed block local inside that action. This is
  harmless on today's corpus, but it weakens the "no execution can
  observe" claim in its docstring.
- **Self-assignment removal.** `finish()` removes `x = x` from real
  translations, not only in `normalize`. That is fine under the IR's
  semantics, but it is an undocumented rewrite, not listed on the
  coverage page.
