## Summary

No confirmed defects. The theorems say what the plan asked for, and the
premises can be discharged together for a real program. I did that
outside the repository: for the corpus forwarder (a real control with a
table and a `checksum16` extern), I built a `Global` whose
`ExternContract` is proved for the reference `P4bloArch.model`, then
applied `build_installedOk` to a real `Installed.build`, then
`entryFrame_ok` to the real `Frame.forBlock`, and finally `initial_ok`.
The repository itself contains no such instance, and the test module
covers only the checker (F1). About 60 hand-written programs gave the same
verdict and the same first code in Python and in Lean. The conformance
counts reproduce: 175 valid programs, 308 validator-test programs, 285
rejected, 34 `DECODE`. The audit has 34 new entries, all on the standard
axioms. Of five mutants, two replicate the builder's and three are my own.
Every mutant is killed where expected. Two rules the proofs do not need
(`noAlias`, and a new one of mine, `writable`) are pinned only by the
conformance test. The findings below are strength gaps and
documentation nits, not errors.

## Confirmed defects

None.

Findings that are not defects:

- **F1. No non-vacuity instance in the repository.** `spec/ir/Tests/Validity.lean`
  (51 lines) runs the checker on the forwarder fixture plus six single
  breaks. No test or example builds a `Global`, a `RunOk` or a
  `MachineOk`, and nothing uses `initial_ok`, `entryFrame_ok`,
  `build_installedOk` or `check_sound` on a concrete program (checked
  with `git grep`). The instance I built needs `native_decide` for the
  concrete facts, such as `check p = .ok idx` and the extern index
  lookups, and the audit forbids that in the repository. A kernel-checked
  version would need either a smaller program or a `decide`-friendly
  index.
- **F2. `ResultOk` does not depend on the block kind.**
  `Progress.lean:44` allows `.error (.parse e)` for a control or deparser
  run too. `runControl` and `runDeparser` (`Interp.lean`, `finished`)
  turn any parse error into an `Except.error` ("parse error … outside a
  parser"). Reading the code, that path cannot be reached: only
  parser-only statements, `enterState`, `select`, `lookahead` and
  `reject` raise `Fault.parse`, and `callBlock` stays within one kind.
  No theorem proves this, though.
- **F3. No composition at the entry points.** No theorem states that
  `runParser`, `runControl` or `runDeparser` of a `Valid` program never
  return an `InterpError`-derived error, given typed arguments, a
  contract-satisfying `Externs` and a built `Installed`. The pieces are
  all there: `initial_ok` matches the `Run` each entry point builds
  (packet for a parser, entries for a control, emitter for a deparser),
  and `entryFrame_ok` matches their `insert` fold. The checks outside the
  machine (`structVar`, "lost its packet") are excluded, and
  `docs/assurance.md` says so.

## The theorem in words

- `MachineOk G m` (`Validity/Machine.lean:81`): the run's shared state
  fits the kind (`RunOk`: same index; a packet for a parser, an emitter
  for a deparser, built entries satisfying `InstalledOk` for a control;
  the extern invariant holds). There is also a context `c` that is a
  block of the valid program with its real scope, of the run's kind,
  with an action of that block when an action body runs (`CtxOk`).
  The frame holds a value of the declared type for every variable the
  context sees, and exactly the action's parameters in the action layer
  (`FrameOk`). When no fault is pending, every item on the continuation
  stack is typed in the context that will be current when it runs
  (`StackOk`). When a fault is pending, it is a parser error the program
  declares, and only the pending block returns are typed (`UnwindOk`).
- `ResultOk G r` (`Progress.lean:44`): `r = .ok ()`, or `r` is a
  `.parse e` with `e ∈ G.p.errors`.
- `progress` (`Progress.lean:57`): one `step` of a `MachineOk` machine
  either finishes with a `ResultOk` result or yields another `MachineOk`
  machine. `Steps.machineOk` and `finishes_documented` extend this to
  every reachable machine and every finite trace, and `drive_documented`
  to the actual runner. This is the progress-plus-preservation shape the
  plan asked for ("never gets stuck except at a documented parser
  error"). "Stuck" means `Fault.interp`, and `ResultOk` excludes every
  `.interp` result by construction.
- Is `MachineOk` satisfiable? Yes, for a real machine. My scratch file
  `ReviewScratch.control_start_ok` builds `Global` for the forwarder
  (`P4blo.Forwarder.program`) with `check_sound`. Its `ExternContract`
  sets `inv e := e.model = P4bloArch.model ∧ e.instances["csum"]? =
  some .checksum16`, and I proved `call` by hand against the real
  `P4bloArch.call`. The run uses `Installed.build idx none` (through
  `build_installedOk`), the frame is the real `Frame.forBlock` (through
  `entryFrame_ok`), and `initial_ok` then gives `MachineOk` for
  `[.statements ingress.body]`, the machine `runControl` starts. It
  compiled with no errors. Its axioms are the standard three plus seven
  `native_decide` axioms, all from the scratch file's concrete
  computations (for example `check p = .ok idx0` and
  `idx0.externInstances.keys = ["csum"]`), none from the repository.
- `.error` reachable for a valid program: only `.parse e` with `e`
  declared. These are `PacketTooShort`, `StackOutOfBounds`, `NoMatch` and
  `ParserTimeout` (core errors, guaranteed through
  `Valid.errors`/`coreErrors`), `verify`'s own error (the rule requires
  it to be declared), and `NoError` on `reject`. No `throwInterp` or
  `liftExcept` error in `Exec.lean`, `Eval.lean` or `Env.lean` survives,
  and the two interpreter mutants below confirm the proof reaches those
  arms.

## Premises

- **`ExternContract`** (`Validity/Invariants.lean:38`): under some
  invariant, a call on a program instance with arguments of the declared
  parameter types succeeds, keeps the invariant, and returns out values
  and a return value of the declared types. This is plausible for all
  five reference families (`spec/arch/P4bloArch/Externs.lean`):
  - `register`: the `out` argument is `Value.zero (bits T)`, the index is
    `bits 32`, and `read` returns `bits (wrap width …)`. This holds if
    the invariant ties the state's `width` to the declaration's `T`
    binding, which `make` does.
  - `counter`: trivially.
  - `checksum16`: I checked it by hand in the scratch proof. The rule
    `[.bits data]` fires, the return is `bits 16`, the outs are empty.
  - `crc16`/`crc32`: `make` stores `config := [D]`, and a typed argument
    has width `D`, so the width check cannot throw.

  Programs whose extern types no family implements (unknown family,
  wrong shape) are accepted by both validators, as my hand cases
  `extern_unknown_family` and `extern_returns_struct` show. They fail at
  `Externs.bind`, before any packet runs. For them the contract holds
  only with an unsatisfiable `inv`, so `RunOk` fails, which is the stated
  load-time boundary. A theorem `P4bloArch.contract : Externs.bind idx =
  .ok e → ∃ C : ExternContract idx, C.inv e` would close the remaining
  premise. The checksum16 case suggests it is a few hundred lines, not a
  research problem.
- **`InstalledOk` and `build_installedOk`**
  (`Validity/InstallLaws.lean:435`): the premise is
  `Installed.build G.idx host = .ok inst`. That is the real
  `P4bloIR.Installed.build` from `Tables.lean:190`, not a restatement. I
  used it unchanged in the scratch instance.
- **"The run fits the block kind"** (`RunOk`): the entry points
  establish it structurally. `runParser` sets `packet := some`,
  `runControl` sets `entries := some entries`, `runDeparser` sets
  `emitter := some {}`, and each sets `index`. The rest stays with the
  caller: `InstalledOk` holds only when `entries` came from `build`, the
  extern invariant holds only for a bound `Externs`, and the parameter
  values must be typed (`entryFrame_ok`'s `hvals`). The entry points
  check none of these three. See F3.

## Vacuity and strength

- `check_sound` and `progress` are both discharged for a real program
  (see above). Neither theorem is vacuous.
- **Rules that keep every theorem when removed.** Removing either of
  these left `lake build P4bloIR ProofAudit` at exit 0:
  - `noAlias ≡ true`, the builder's mutant 2, which I replicated.
  - `writable ≡ true`, my own mutant. It lets assignments go through
    `in` and directionless params.

  Only `tests/test_lean_agrees_validity.py` kills them, with four
  disagreements each. A `git grep` of the progress-side modules
  (`StepLaws`, `StmtLaws`, `CallLaws`, `EvalLaws`, `FrameLaws`,
  `ValueLaws`, `InstallLaws`, `Machine`, `Invariants`, `Progress`) finds
  no reference to: `noAlias`, `actionsAcyclic`, `blocksAcyclic`,
  `entriesDistinct`, `keyNames`, `oneLpm`, `noMix`, `exportRoles`,
  `signatureOk`, `NamesOk`, `writable`, `headersType` or `metadataType`.
  So by name, progress needs the typing, placement, scope, kind and
  core-error rules, and not the name, alias, acyclicity, tie, export or
  writability rules. Acyclicity belongs to termination (C2), which is
  still open. Only the two rules above are confirmed by mutation; the
  rest is by reading.
- **Can a checker accept a badly typed assignment while progress still
  holds?** Not without breaking a proof. `FrameOk.vars` keeps
  `ValueHas` at the declared type, widths included, so `writeLValue_ok`
  needs the assigned value to have the lvalue's type. The builder's
  mutant 3 (emit) shows the same thing for a rule the machine relies on.
  I did not re-run an assignment mutant, because dropping the premise
  from `StmtTyped.assign` requires matching edits in `Sound.lean` before
  it tests anything.
- The invariant is stronger than the machine strictly needs, since
  widths are tracked exactly. That is fine: `initial_ok` shows real
  machines satisfy it.

- **Does `DECODE` hide a semantic gap?** No. The Lean decoder rejects
  only wire shapes, so a Lean `DECODE` always names a wire problem.
  However, `corresponds` accepts `DECODE` when Python's first code is
  `NAME_EMPTY`/`NAME_DUPLICATE`, or when any later Python diagnostic is
  `DECODE`-capable. Because of that, three validator-test programs never
  exercise the Lean rule they target:
  - `test_name_duplicate[2]#138`: a duplicate action param whose
    direction is unspecified.
  - `test_name_duplicate[7]#143`: the same, for an extern method param.
  - `test_noaction_reserved[1]#161`: `NoAction` with an
    unspecified-direction param.

  I checked those three rules by hand with well-formed wire programs
  (`extern_method_param_dup`, `action_param_dup`,
  `noaction_with_param`), and Lean gives the same code as Python. The
  gap is in test coverage only; fixing the Python tests to use a
  specified direction would close it.
- **Can Lean reject a program Python accepts?** I did not find one.
  Hand-written programs, run through `p4blo-lean check` and
  `validator.validate` (scripts `scratchpad/rv/cmp*.py`), covering:
  - struct cycles, including mutual `A -> B -> A`;
  - a three-deep struct chain ending in a stack, which checks that the
    `tyDeep` fuel bound is tight but sufficient;
  - an unknown struct field, an empty header, `bit<0>` and stack size 0
    locals, and a zero-width literal;
  - `==` and mux on structs, and shifts with a wider right operand;
  - select on enum, error and boolean keys, and masked sets on a
    boolean key;
  - boolean `lookahead`, `lastIndex`, a boolean stack index, and a
    literal stack index out of range;
  - extern results: missing, wrong type, a read-only target, and a wrong
    argument together with a wrong result;
  - a `bit<0>` extern return;
  - leading-zero literals and entries (`"007"` vs `"7"` →
    ENTRY_DUPLICATE in both), and an empty literal value (LITERAL_FORMAT
    vs DECODE, per the table);
  - key-name clashes between `name` and a dotted path;
  - namespace clashes: a header named like a block, a local like a
    table or an action, an instance like a table, an error like a
    struct;
  - ten multi-error programs checking first-code order: cast, mux, table,
    select, entry, call, block params and exports.

  All agree on acceptance and on the first code. The only difference is
  in paths, which the test does not compare: for a mutual struct cycle,
  Python reports the struct whose field closes the cycle
  (`struct_types[3]`) and Lean the first struct that fails `tyDeep`
  (`struct_types[2]`).

## Documentation

  `build_installedOk` and `initial_ok`/`entryFrame_ok`: each matches its
  theorem. The `progress` row lists the right exclusions. Its phrase
